## Формат server.env

`server.env` — построчный файл данных `КЛЮЧ=значение`, а не shell-скрипт. Менеджер не выполняет `source`, `eval`, команды в `$(...)` или обратных кавычках и не подставляет `$VAR`.

- Пустые строки и строки с `#` после отступа пропускаются. Строки без `=` обычное чтение игнорирует; строгая проверка (`strict=True`) отклоняет их с `ValidationError`. Требование наличия файла (`require_exists`) отдельно сохраняет прежний `RuntimeError` при его отсутствии.
- Пробелы по краям ключа убираются; префикс `export ` (также с табуляцией) снимается. Все ключи, включая неизвестные менеджеру, приводятся к верхнему регистру. Значение отделяется по первому `=`, остальные знаки `=` сохраняются.
- Комментарий начинается с `#`, перед которым стоит пробел или табуляция, вне кавычек. `a#b` и `#literal` сразу после `=` — буквальные значения; `KEY= # комментарий` задаёт пустое значение.
- Кавычки открывают группу в начале значения или после пробела/табуляции. Апостроф внутри слова (`it's`) остаётся буквальным. Одна парная внешняя оболочка `'…'` или `"…"` снимается, вложенные кавычки сохраняются. Непарные кавычки остаются данными; `#` внутри незакрытой группы не начинает комментарий.
- В двойных кавычках декодируются только `\"` → `"` и `\\` → `\`. В одинарных кавычках и вне кавычек обратный слеш буквальный; остальные escape-последовательности, например `\n`, не превращаются в специальные символы. При записи нормализованные ключи и значения с разделителями строк (включая LF, CR и Unicode-разделители) отклоняются с `ValidationError` до изменения файла и временной копии. Shell-конкатенация не поддерживается.
- Пробелы по краям значения вне кавычек убираются, внутри внешней пары сохраняются. Пустые значения, CRLF, `#` в кавычках и знаки `=` поддерживаются.

Например:

```dotenv
  export manager_timezone = Europe/Moscow # основная зона
CUSTOM_TEXT="  a # b  "
CUSTOM_PATH="C:\\data\\file"
CUSTOM_QUOTES="say \"hello\" # literally"
```

При чтении получаются ключ `MANAGER_TIMEZONE` со значением `Europe/Moscow`, текст с сохранёнными крайними пробелами, путь с буквальными обратными слешами и текст `say "hello" # literally`.

Если несколько строк после нормализации дают один ключ, действует последняя строка. При записи словаря разные исходные ключи, совпавшие после нормализации, объединяются только при одинаковых значениях; при разных значениях запись отклоняется с `ValidationError` до изменения файла.

Запись сохраняет прежний вид простых значений. Если повторное чтение изменило бы значение, запись добавляет двойные кавычки и экранирует в них `"` и `\`. Один и тот же сериализатор используется для рабочего файла и переносимого `server.env` в бэкапе, поэтому повторное чтение после записи сохраняет однострочные значения. Исходные комментарии и оформление строк не сохраняются. Известные ключи идут в установленном порядке, остальные — по алфавиту; файл заменяется атомарно с правами `0640` и владельцем `root:xray`.

Точечные изменения выполняются под `manager.lock`: значения по умолчанию заполняют только отсутствующие ключи (пустые остаются пустыми), затем удаляются выбранные ключи, затем применяются изменения. Неизвестные поля сохраняются с нормализованными именами. Полная запись и восстановление остаются отдельными операциями.

## Резервные Копии Данных

Архив данных создаётся командой:

```bash
xray-backup create
```

В архив входят:

```text
/usr/local/etc/xray/config.json
/usr/local/etc/xray/server.env
/usr/local/etc/xray/manager.db
/etc/caddy/Caddyfile, если Caddy настроен
/etc/caddy/conf.d, если Caddy site configs существуют
```

Архивы хранятся на сервере в `/root/xray_backups`.
Архив содержит Reality private key, UUID клиентов, Trojan passwords, SQLite-базу менеджера, статистику трафика, журнал активности, глобальные блокировки, исключения suspicious, token Telegram-бота и Caddy site configs, поэтому его нужно хранить как приватный секрет.
Перед добавлением `manager.db` в архив `xray-backup create` создаёт временный консистентный SQLite snapshot через SQLite backup API внутри `/root/xray_backups`, а не копирует живой файл базы напрямую. Это защищает архив от повреждения, если фоновые таймеры или бот записывают данные во время создания backup. Snapshot включает транзакции, которые ещё лежат в `manager.db-wal`, а в архив попадает один самостоятельный файл базы в обычном режиме журнала, без `-wal` и `-shm`, как и раньше.

Обычный `xray-backup` теперь включает настройки Caddy, чтобы Trojan TLS/WebSocket и VLESS TLS/XHTTP подключения восстанавливались вместе со связанными Caddy site configs. Сертификатный кеш Caddy не копируется: Caddy может выпустить сертификаты заново после восстановления. Для legacy direct TLS/TCP подключений в backup сохраняются пути `certificateFile` и `keyFile`, но не сами cert/key файлы. После restore менеджер автоматически выставляет безопасные права для существующих файлов: cert `root:xray 0644`, key `root:xray 0640`; если файл отсутствует, restore выводит warning до проверки и перезапуска Xray. Статические файлы сайта не входят в общий backup; для них остаются отдельные backup-пункты в меню `Подключения и TLS` -> `Caddy / TLS` -> `Бэкапы`.

`server.env` сохраняется как переносимая конфигурация. Host-specific значения `SERVER_ADDR`, `SECURITY_AUDIT_LAST_RUN` и `MANAGER_PYTHON` в новый архив не записываются. При восстановлении `xray-backup restore` сохраняет их текущие значения на целевом сервере, а значения из архива (если архив создан старой версией и содержит их) не переносит: `SERVER_ADDR` остаётся адресом нового сервера, чтобы новые VLESS-ссылки генерировались с актуальным адресом, а `MANAGER_PYTHON` — путём к Python 3.12+ этого сервера, который записан в первую строку команд `/usr/local/sbin/xray-*` (см. [Python 3.12](installation.md#python-312)). Если на целевом сервере такого ключа нет, после restore его тоже не будет.

Показать бэкапы на сервере:

```bash
xray-backup list
```

Удалить бэкап с сервера:

```bash
xray-backup delete /root/xray_backups/ИМЯ_АРХИВА.tar.gz
```

Через меню `Резервные копии` -> `Удалить бэкап` архив выбирается из таблицы, после этого нужно подтвердить удаление.
Удаление бэкапа не меняет текущие данные Xray.

Создать бэкап и скачать на компьютер, с которого выполняется подключение:

```bash
xray-backup create
scp root@SERVER_HOST:/root/xray_backups/ИМЯ_АРХИВА.tar.gz BACKUP_DESTINATION/
```

Через меню `Резервные копии` -> `Создать бэкап и показать команду скачивания` сервер создаст архив, спросит путь для сохранения и покажет готовую команду `scp`.
В меню можно выбрать систему компьютера, где будет выполняться `scp`, чтобы подставить подходящую папку загрузок по умолчанию.
Эту команду нужно выполнить в терминале на компьютере, с которого выполняется подключение.

Загрузить архив обратно на сервер перед восстановлением:

```bash
scp BACKUP_ARCHIVE_PATH root@SERVER_HOST:/root/xray_backups/
```

Восстановить данные из архива, который уже лежит на сервере:

```bash
xray-backup restore /root/xray_backups/ИМЯ_АРХИВА.tar.gz
```

Restore выполняется в таком порядке:

1. Менеджер проверяет состав архива до любых изменений: если в нём нет `config.json`, `server.env` или `manager.db`, restore завершается ошибкой `Backup does not contain required file: …`, ничего не останавливая и не перезаписывая.
2. Берёт блокировку `/usr/local/etc/xray/manager.lock`; до неё restore только читает архив и ничего на сервере не меняет. Если другая операция менеджера держит её дольше 60 секунд, restore завершается без изменений с сообщением `Другая операция менеджера ещё выполняется: …`. Пока restore держит блокировку, команды, которые берут её же (`xray-client`, `xray-set-cascade`, `xray-set-bypass`, `xray-warp`, `xray-telegram` и соответствующие пункты меню), ждут до 60 секунд и затем завершаются без изменений.
3. Запоминает состояние Xray и активные units менеджера: `xray-traffic-sync.timer`, `xray-raw-log-rotate.timer`, `xray-client-expire.timer` и `xray-telegram-poller.service`. Останавливает эти таймеры, их сервисы и poller, затем отдельно останавливает Xray с таймаутом 30 секунд. Его штатный `ExecStop` сохраняет последние счётчики трафика в текущую базу до её замены. Ошибка или таймаут остановки запрещает копирование архива.
4. После остановки Xray создаёт pre-restore бэкап текущего состояния. Отдельную синхронизацию restore не запускает; счётчики, успешно сохранённые через `ExecStop`, уже входят в снимок. Если `ExecStop` не смог сохранить трафик, остаются значения последней успешной синхронизации. Если на сервере уже есть `/usr/local/etc/xray/manager.db`, дополнительно создаётся отдельная pre-restore копия SQLite-базы в каталоге резервных копий. Обе копии включают данные из `manager.db-wal`; если SQLite backup API недоступен, запасная копия файла базы сохраняется вместе с её `-wal`.
5. Удаляет `manager.db-wal`, `manager.db-shm` и `manager.db-journal` прежней базы: иначе SQLite при следующем открытии наложил бы их на восстановленный файл. Затем применяет файлы и Caddy config из архива, если он там есть, выполняет `caddy validate` и reload Caddy, проверяет `config.json`, запускает Xray и в течение 3 секунд проверяет, что `xray.service` остаётся активным, а TCP-порты inbound из восстановленного `config.json` принимают соединения. Старый экземпляр Xray к этому моменту остановлен, поэтому его счётчики не записываются в восстановленную базу.
6. Запускает обратно только те units, которые были активны до restore. Таймеры и poller, намеренно выключенные на сервере, restore не включает. Если запустить их не удалось, команда завершается с кодом 1 и печатает команду `systemctl start …` для ручного запуска.

Если применение архива завершается ошибкой — Caddy или Xray проверка не проходит, Xray падает после запуска, копирование прерывается, — restore ещё раз останавливает Xray до обратного копирования, откатывается к pre-restore бэкапу, запускает Xray и ранее активные units менеджера и завершается с кодом 1: `ERROR: Restore failed: ПРИЧИНА`. Если не удался и откат, сообщение содержит обе причины (`ПРИЧИНА; rollback failed: …`); тогда проверь сервер через `xray-test` и восстанови pre-restore бэкап из `/root/xray_backups` вручную. Ошибка остановки перед откатом запрещает перезапись базы работающего экземпляра.

При ошибке до начала копирования (например, не удалось создать pre-restore бэкап) исходные файлы остаются на месте, и restore пытается вернуть Xray, если он был активен до операции, затем запускает ранее активные units менеджера. Если восстановить работу Xray не удалось, сообщение дополнительно содержит `original Xray restart failed: …`.

На новом сервере, где таймеры менеджера ещё не включены, restore их не включит: включи их после restore явно и проверь `systemctl list-timers`.
Если архив переносится на сервер с новым IP или доменом, сначала установи менеджер на новом сервере, затем восстанови архив. `SERVER_ADDR` из нового `server.env` будет сохранён, а старый адрес из архива не перезапишет новый.


## Резервные Копии Caddy

Настройки Caddy входят в обычный `xray-backup`, если Caddy настроен. Отдельные операции ниже нужны для точечного config-only backup/restore перед ручными изменениями Caddy или без восстановления Xray/SQLite.
В backup Caddy входят:

```text
/etc/caddy/Caddyfile
/etc/caddy/conf.d
```

Архивы Caddy config хранятся в `/root/xray_caddy_backups`.
Сертификатный кеш Caddy не копируется: Caddy может выпустить сертификаты заново после восстановления.

Операции с Caddy config доступны через меню:

```text
Подключения и TLS -> Caddy / TLS -> Бэкапы -> Создать backup Caddy config
Подключения и TLS -> Caddy / TLS -> Бэкапы -> Показать backups Caddy config
Подключения и TLS -> Caddy / TLS -> Бэкапы -> Восстановить Caddy config из backup
Подключения и TLS -> Caddy / TLS -> Бэкапы -> Удалить backup Caddy config
```

Перед восстановлением Caddy config менеджер автоматически создаёт pre-restore backup текущих настроек Caddy, затем применяет выбранный архив, выполняет `caddy validate` и reload Caddy. Если проверка не проходит, менеджер пытается вернуть предыдущие настройки из pre-restore backup.

Файлы сайта сохраняются отдельным архивом. Меню пытается найти папку сайта по директивам `root * ...` в `Caddyfile` и site configs, но путь можно ввести вручную.

Архивы сайта хранятся в `/root/xray_caddy_site_backups`.

Операции с файлами сайта доступны через меню:

```text
Подключения и TLS -> Caddy / TLS -> Бэкапы -> Создать backup сайта
Подключения и TLS -> Caddy / TLS -> Бэкапы -> Показать backups сайта
Подключения и TLS -> Caddy / TLS -> Бэкапы -> Восстановить сайт из backup
Подключения и TLS -> Caddy / TLS -> Бэкапы -> Удалить backup сайта
```

Перед восстановлением сайта менеджер создаёт pre-restore backup текущей папки сайта, если она существует, затем заменяет её содержимое файлами из выбранного архива. Caddy config и сертификаты при этом не меняются.


## SQLite Данные

SQLite-база менеджера хранится в:

```text
/usr/local/etc/xray/manager.db
```

`install.sh` создаёт эту базу сразу. Клиенты, VLESS/Trojan-подключения, трафик, журнал активности, исключения suspicious, Telegram-настройки, подписки, флаг личных уведомлений активности и настройки оплаты хранятся в `manager.db`.

Подробная схема таблиц и индексов описана отдельно: [Схема базы данных](database-schema.md).

База работает в режиме WAL (`journal_mode=wal`) с `synchronous=NORMAL`. Запись сначала попадает в `manager.db-wal`, поэтому Telegram-бот и меню читают базу, не дожидаясь, пока минутный таймер зафиксирует свою запись. Синхронизация с диском (fsync) выполняется при переносе журнала в базу (checkpoint), а не на каждую транзакцию. Во время работы рядом с базой лежат `manager.db-wal` и `manager.db-shm`. Это норма: SQLite создаёт их с теми же владельцем и правами, что у базы (`root:xray`, `0640`), и удаляет при закрытии последнего соединения. После пиков записи `manager.db-wal` усекается до 128 МБ.

Режим хранится в самом файле базы. Базу, созданную раньше в режиме `delete`, в WAL переводит первая команда или таймер менеджера, которые открывают её для записи: минутный `xray-traffic-sync.timer`, `xray-client`, Telegram-бот. `xray-test` и `xray-vps-manager sqlite status` только читают базу и режим не меняют. Если база занята, переключение откладывается до следующего открытия.

При `synchronous=NORMAL` внезапная потеря питания или сбой ОС могут откатить последние зафиксированные транзакции (обычно последний прогон минутного таймера), но не повреждают базу. Итоги трафика и счётчики последнего замера пишутся в одной транзакции, поэтому остаются согласованными. Однако трафик, учтённый в откатившихся прогонах, теряется: после такого сбоя Xray перезапускается и считает трафик заново с нуля. Трафик с последнего прогона до сбоя теряется при любом режиме журнала.

Не копируйте `manager.db` вручную без `manager.db-wal`, пока работают таймеры или бот: часть последних изменений может лежать только в `-wal`. Для копии используйте `xray-backup create`.

Проверить состояние базы:

```bash
xray-vps-manager sqlite status
```

Эта команда показывает путь к базе, версию схемы, результат `PRAGMA quick_check`, готовность SQLite и количество строк в основных таблицах, включая activity blocklist и hit-счётчики. То же доступно через меню `Сервис и диагностика`:

```text
SQLite: статус базы
```

Обычная диагностика `xray-test` проверяет наличие базы, версию схемы, режим журнала, ready-метку, счётчики и согласованность runtime-строк без полного физического прохода по SQLite-файлу. Строка `Manager SQLite DB` показывает `journal=wal`; файлы `manager.db-wal` и `manager.db-shm` проверка считает нормой. `WARN` выводится, если база не в режиме WAL (`journal_mode=delete, expected wal`) или рядом с ней остался откатный журнал `manager.db-journal`. Если нужно именно проверить целостность страниц базы через `PRAGMA quick_check`, запускайте:

```bash
xray-test --all
```


## Автоматические Технические Бэкапы

Перед постоянными изменениями Xray config менеджер создаёт технический бэкап текущего конфига.

Бэкапы конфига лежат рядом с основным конфигом:

```bash
/usr/local/etc/xray/config.json.bak.*
```

Перед правкой, переименованием или удалением Caddy site config и перед правкой `Caddyfile` менеджер сохраняет копию файла рядом с ним:

```bash
/etc/caddy/conf.d/DOMAIN.caddy.bak.*
/etc/caddy/Caddyfile.bak.*
```

Копия нужна для отката, если `caddy validate` или reload не прошли. После успешной операции рядом с каждым файлом остаются 5 самых новых копий, более старые удаляются; накопленные раньше копии сокращаются при первой успешной правке этого файла. Caddy подключает только `conf.d/*.caddy`, поэтому копии не влияют на конфигурацию.

Бэкапы предыдущих версий Xray лежат здесь:

```bash
/usr/local/lib/xray-backups
```

Если новый конфиг не проходит проверку или Xray после перезапуска не остаётся активным либо не открывает порты inbound (проверка длится 3 секунды), менеджер восстанавливает предыдущий конфиг и перезапускает Xray.
