Корневые команды - это тонкие совместимые точки входа для ручного запуска и автоматизации. `install-caddy-download-proxy.sh` и `caddy-menu` относятся к отдельному Caddy-only сценарию второго download endpoint и не ставят основной Xray manager. Основной код находится в Python-пакете `xray_vps_manager`: команды в `commands`, общая инфраструктура в `core`, логика клиентов в `clients`, трафик в `traffic`, активность в `activity`, работа с Xray config в `xray`, Telegram-бот в `telegram`, SQLite-слой в `db`, системные сценарии (интерпретатор команд, генерация и доставка systemd units) в `system`. Модуль `system/sqlite_admin.py` создаёт и мигрирует базу менеджера и собирает сведения для `sqlite status`.

`runner.py` задаёт общую обработку ошибок, проверку root и вход в команды; `commands/arguments.py` проверяет форму argv до рабочих операций. Контракт описан в [CLI](cli.md). Версия во время выполнения берётся из `xray_vps_manager.__version__`; тест сверяет её с меню и `pyproject.toml`.

`core.settings` задаёт единые чтение, нормализацию и сериализацию [server.env](backups-and-data.md#формат-serverenv), включая переносимую копию в бэкапе. `core.server_env` сохраняет совместимые имена функций. `update_env` выполняет точечное изменение под `manager.lock`, `write_env` — полную запись, `env_text` формирует текст без записи файла.

`xray.email` разбирает и формирует email клиентов Xray; прежние имена в `clients.models` сохранены для совместимости. `xray.client_routes` строит правила по переданным данным, включая список email. `clients.routes` управляет метаданными и выбором клиентских маршрутов и применяет runtime override, а `clients.credentials` разрешает email по данным клиента. Подготовка правила предшествует разрешению credentials, сохраняя прежний порядок операций при ошибке.

`xray.invariants.validate` проверяет инварианты кандидата без его изменения и без чтения БД. `xray.apply.apply_config` проверяет их и кандидат командой `xray run -test -format json` до записи; при совпадении байтов не создаёт копию и не перезапускает Xray. При изменении он сохраняет копию, атомарно записывает конфиг и по умолчанию перезапускает сервис с проверкой старта и локальных портов в течение полного окна 3 секунды. При ошибке после изменения он пытается восстановить прежние байты и, если рестарт включён, проверить рестарт отката. `ApplyResult` сообщает об изменении, копии, рестарте и проверенных портах; `ApplyConfigError` — о стадии и результате отката. Блокировка `manager.lock`, изменения БД и `server.env` остаются ответственностью вызывающего сценария. После создания копии и до замены файла выполняется ротация по возможности: общий лимит — 20 подходящих копий рядом с конфигом, включая защищённую текущую; при ошибках чтения или удаления их может остаться больше. В неё входят обычные имена `config.json.bak.<stamp>` с 14 или 20 цифрами и исторические `config.json.bak.telegram.<stamp>` с 20 цифрами; другие имена, ссылки, каталоги и другие расположения не затрагиваются. При совпадении байтов ротация не выполняется; подробности — в [описании технических копий](backups-and-data.md#автоматические-технические-бэкапы).

К `apply_config` подключены клиентские операции с перезапуском, изменение Reality, BitTorrent, WARP, каскад, bypass, маршрут Telegram, blocklist и GeoIP warning в меню. Клиентские `add`, `remove`, `disable`, `enable` и `move-connection`, а также Telegram и blocklist записывают БД первыми с точечной компенсацией при ошибке. Остальные переходные клиентские операции с применением конфига, Reality, каскад, bypass и WARP пока сохраняют порядок «конфиг → БД». Подготовка постоянных кандидатов WARP, каскада, bypass, Telegram, blocklist и GeoIP warning перемещает существующее правило `api` на первое место, сохраняя порядок остальных правил; валидатор сам порядок не исправляет. Другие пути ещё могут использовать прежний `save_config`. Отдельные диагностические пробы каскада, bypass и WARP используют `temporary_config`: предварительная проверка кандидата, проверяемые рестарты и возврат исходных байтов без технической копии и ротации. `xray.apply.apply_config_after_probe` объединяет временную пробу `create`/`enable`/`disable` WARP с применением чистого итогового конфига: сравнение и техническая копия используют исходные байты до пробы; при совпадении выполняется возврат без копии и ротации. `disable` сначала читает маршрутную SQLite-базу и подготавливает выключенный маршрут; только при отсутствии изменений выполняется отдельная диагностическая проба без постоянного применения. Подробности проверок и восстановления — в [описании WARP](cascade-and-warp.md#warp). Для restore, обновления и ручного перезапуска из меню `restart_installed_config` проверяет и обязательно запускает установленный конфиг без его перезаписи и технической копии; откат архива, бинарника или assets остаётся за внешним сценарием. Ручная проверка меню использует общую сборку команды проверки, сохраняет потоковый вывод и не создаёт копию и не запускает ротацию.

Для `remove` клиента сначала берётся `manager.lock`, затем `activity.lock`. Блокировка активности удерживается до завершения применения или отката, чтобы парсер не продвинул offset при временном отсутствии записи клиента. `ExecStop` использует `traffic.lock` и не ждёт `activity.lock`.

## Локальные тесты и CI

Текущий код требует Python 3.12+. Полный набор из корня репозитория:

```bash
python3.12 -W error::DeprecationWarning -m unittest discover -s tests -t .
```

`tests` — импортируемый пакет; работают также обычный discovery с `-s tests` и изолированный запуск `python3.12 -I -S -B -W error::DeprecationWarning -m unittest discover -s tests -t .`. Добавлять каталог `tests` в `PYTHONPATH` не требуется. Тесты используют временные файлы, подмены процессов и HTTP; отдельные регрессии создают локальные процессы и привязывают loopback-порты.

GitHub Actions (`.github/workflows/tests.yml`) запускает unittest на Python 3.12 и 3.13 для pull request и push в `dev`/`main`. Новых Python-зависимостей нет. Ключ `-W error::DeprecationWarning` превращает предупреждения этого типа в ошибки в основном процессе `unittest`. Дочерние интерпретаторы Python используют собственные настройки предупреждений.

## Архитектурные проверки

`tests/test_architecture.py` проверяет импорты между слоями; переходный allow-list содержит 5 пар и может только сокращаться. Оставшиеся исключения относятся к зависимостям клиентских операций от трафика; `xray` не импортирует `clients`. Отдельный `tests/fixtures/architecture-markers.json` фиксирует существующие AST-вхождения операций и рабочих путей. Новое вхождение ломает тест, устранённое требует удаления записи из baseline. Номер строки не участвует в идентичности: учитываются модуль, функция/класс, категория, AST и число повторений.

Проверяются `print`, `input`, `sys.exit`, `SystemExit`, `open`, импорты и обращения к `subprocess`/`sqlite3`, строки с `/usr/local/` вне `core.paths`. Разрешения заданы по роли модуля: вывод в интерфейсах и `core.terminal`, ввод-вывод в явно перечисленной инфраструктуре. `subprocess.CalledProcessError`, `TimeoutExpired`, `CompletedProcess` и импорты, используемые только для этих имён, разрешены. Настоящие docstring не считаются рабочими путями; строки шаблонов units учитываются. Это статическая проверка перечисленных маркеров, а не полное определение всех способов ввода-вывода Python.
